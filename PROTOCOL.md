# Client delivery protocol v1

Butchr registers its durable deployment UUID and process-memory session UUID with authenticated `POST /v1/register`. The JSON receipt contains only server/authorization identity and registration acknowledgement. Periodic registration writes maintain last-seen; they never deliver state. The older `/v1/connect` response is retained for compatibility, but the current client never uses it or falls back to polling.

Canonical delivery is `GET /v1/events`, `Accept: text/event-stream`, with `Authorization: Bearer …`, `X-Butchr-Deployment-Id` and `X-Butchr-Session-Id` headers. The session must already be registered under that authorization. Credentials never enter URLs. Browser Origin/fetch-site requests are rejected; clients cannot use the admin API with their key. Admin origin/CSRF/same-user protections remain intact.

Every open starts a new epoch and sends `event: snapshot` with `id: <epoch-UUID>:0`, and JSON `{revision, state, resync:true}`. State is the complete `{serverId,authorizationId,briefs,remoteRules}` document. This is explicit snapshot resynchronization, **not replay**: Last-Event-ID does not request replay and is deliberately ignored. Reconnect always replaces all previously staged remote state, including empty collections. IDs are process-memory stream identifiers, not persistent database revisions.

Committed changes send `event: patch`, incrementing sequence numbers within that stream. JSON is `{baseRevision,revision,patch:[…]}`. The SSE `id` must match revision. Protocol v1 emits the RFC6902 subset `replace /briefs` and `replace /remoteRules` with complete changed collections. Deletion, including the final record, replaces the relevant collection with its authoritative empty value; this avoids array-index ambiguity. Both operations in one event apply to a clone, in order; only a fully valid resulting document is atomically made visible. Unknown operations/paths, malformed values, provenance failures and gaps invalidate the stream and trigger a new snapshot. Duplicate/older patch sequence IDs in the same epoch are ignored. No patch is accepted before the snapshot.

The client uses pinned `eventsource` with a custom fetch in Bun to attach headers and reject redirects, rather than browser EventSource URL tokens. `fast-json-patch` supplies RFC6902 validation/application, with prototype traversal blocked and protocol paths restricted before application. Full brief/rule validators and source identity checks run before state replacement. Remote state is memory-only; local/custom data is untouched. Rules remain staged, never controller input.

Named heartbeat events every10seconds carry the current revision. Only valid snapshots, patches and matching heartbeats refresh the30second client watchdog. Errors, revocation, invalid patches, disconnect or idle timeout clear staged remote state and close the old EventSource before jittered exponential reconnect (up to30seconds). Registration failures also clear state. Configuration and connection generation guards reject late callbacks. Cancellation settles initial-connect waiters. Reconnect retains deployment and session identity; restarting the client retains only deployment identity.

Resource bounds:2 active streams per registered authorization/deployment, shared across all its sessions and both normal and provider-protocol streams; no global or per-authorization stream-count cap;96MB maximum encoded frame and per-stream owned queue,192MB aggregate owned queues. Server pull hands Bun at most64KiB per chunk with no ReadableStream prefetch queue; overflow, abort or shutdown discards owned frames and releases bookkeeping. No replay history is retained. Client raw SSE frames are bounded before parser buffering, including split chunks and LF/CRLF/CR boundaries. HTTP registration responses are capped at4KiB. Stored brief/rule library limits still apply.

## References and distinction from LaunchDarkly

- [Official LaunchDarkly JavaScript shared SDK stream transport](https://github.com/launchdarkly/js-sdk-common/blob/main/src/Stream.js): EventSource abstraction, reconnect backoff and stream timeout inspired lifecycle handling.
- [Official LaunchDarkly JavaScript shared SDK event handlers](https://github.com/launchdarkly/js-sdk-common/blob/main/src/index.js): `put` replaces flags; `patch` updates a flag by key/version; `delete` removes a versioned flag. Those payloads are **not RFC6902**. Butchr borrows the snapshot/update lifecycle, not that wire format.
- [RFC6902](https://www.rfc-editor.org/rfc/rfc6902): ordered JSON Patch operation arrays and operation failure semantics. Butchr intentionally restricts the operation/path vocabulary and validates the whole candidate before publishing it.
- [Official EventSource package documentation](https://github.com/EventSource/eventsource): supported Bun runtime and custom fetch for authentication headers.


## Global brief library

Brief records are global, authenticated server-owned configuration. Every valid authorization receives the same UUID/name/text library; rules remain scoped. A global mutation fans out to every authorization stream. Client remote reference prefixes retain server+authorization transport provenance for compatibility; the brief UUID itself is unchanged by promotion and is not authorization ownership. Limits:1000 records and64MB JSON of id/name/text, leaving frame headroom for rule data and metadata. The client accepts1000 records. Legacy promotion and save use the same budget; over-limit migration fails before changing records.

## Upstream operational events

`POST /v1/instance-events` uses the existing Bearer key, machine-only guards and JSON body `{deploymentId,sessionId,events:[...]}`. The tuple must already be registered under that authorization. Keys are authorization-level shared secrets, not hardware attestation; a second holder of the same key cannot be distinguished cryptographically. No new persistent credential or device access is created.

Each event is `{id,sequence,occurredAt,type:"session.snapshot",data}`. UUID IDs and contiguous sequences are scoped to server/origin/authorization/deployment/session. Data is an exact allowlist: mode, controllersEnabled (boolean or unknown/null), remoteConfigsEnabled, transportConnected, agentsChecked, agentsTruncated, and at most100 agents with SHA256 opaque id, idle/working/blocked/done/unknown status, confirmedAt. Canonical UTC timestamps are validated; raw arbitrary strings/unknown fields are rejected. Max32KiB/event,16events/batch,1MiB request. Snapshots replace the session projection atomically in sequence; declined observations do not claim a fresh full census.

Batches are transactional. Duplicates acknowledge the durable cursor without reapplying state; conflicting retained sequence/ID reuse and gaps reject the batch. Latest projection/cursor persists through restart and journal retention. The journal stores only IDs/digests, bounded to64/session,1024/authorization,4096global and14days. Historical known-session events remain admissible and are displayed stale using source time; unknown/cross-authorization tuples and revoked keys reject. Received time does not turn old observations into fresh activity.

The client persists admitted snapshots before upload in a private64-record/2MB outbox with at most10000 source-scoped cursors, retries with jittered exponential backoff capped30seconds, and removes records only after acknowledgement. Capacity pauses admission explicitly rather than silently evicting events. Old-source records are not sent under a new authorization; returning to the earlier source retains its sequence cursor. A lifetime SQLite exclusive writer lock prevents concurrent clients from overwriting one runtime's state and is kernel-released on crash. JSON installs fsync/rename/directory-sync; post-rename memory retains installed cursors even on sync failure. Stop cancels HTTP work and ignores late acknowledgements.

## Local overrides and shutdown

The local master switch gates every remote configuration consumer; remote briefs disappear from the effective library while off, and rule DTOs explicitly distinguish master-off, local override and server-disabled. Per-rule intent is a persistent tombstone keyed by the immutable remote reference. Deletion/reappearance and patches retain it. Transport/event reporting may continue; local/custom data is untouched. Rules are staged-only in the Codey management host, so no live worker lifecycle is triggered.

On shutdown the server starts native Bun stop before closing owned SSE streams. This ordering avoids a reproduced Bun two-EventSource finalization hang; no force-exit or network security change is used.

Public HTTPS mode (explicit canonical-origin configuration) uses the same protocol and snapshot/resync semantics. It uses the same two-stream per-deployment admission rule and a narrower96MB aggregate owned-queue budget; other frame/queue and client bounds remain unchanged. All backend routes additionally require the verified same-UID loopback TLS proxy. Neither forwarded client IP nor a supplied proxy header is a credential. Body reads have a five-second deadline,1MiB actual-byte bound (4KiB authentication), and16-handler admission cap. Production credential-rate bookkeeping is bounded to2048 identities/window; unknown keys do not allocate rate entries.
